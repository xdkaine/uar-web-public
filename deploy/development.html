Development delivery

Source branch: dev. Generated deployment branch: deploy/dev. Production remains a separate release.

Bootstrap configuration: application rollout requires development HTTPS origins, runtime secrets, explicit external-service network allowances and a successful image build. Cluster installation alone does not demonstrate application readiness.

Push to deployment

  1. GitHub-hosted runners lint and test portal and auth source.
  2. After checks, build five images with the configured public URL and Turnstile key. Runner builds reject project secrets, tests and unintended source files.
  3. Publish images to GHCR and collect all five digests from the same source commit.
  4. Generate immutable release directories and update deploy/dev only if that commit is still the dev tip.
  5. Flux pulls deploy/dev. Infrastructure must become healthy; the migration Job serializes portal, auth and runtime grants under a database advisory lock; application rollout waits for that release's migration success.

Operational boundaries

  • Existing development data is preserved through an explicit restore and cutover. Templates alone do not import Docker data.
  • Only migration jobs receive schema privileges; application roles remain separate. PostgreSQL uses TLS with a dedicated CA.
  • No schedulers or external administrative workflows are enabled by deployment.
  • Local-path persistent volumes use Retain. Requested storage is a planning budget, not a filesystem disk quota. Monitor host free space and provision capacity before data grows.
  • Failed migration jobs remain for diagnosis; do not delete/retry them without reconciling database state. Advisory-lock connection loss cancels child processes but cannot make external process termination atomic.
  • Rollback requires compatible schema. Reverting an image cannot undo one-way migrations or recover lost data.
  • Protect dev and deploy/dev: permission to change deployment code is permission to run code in development. Do not run untrusted PR jobs on the application server.

Docker development cutover

  1. Verify Compose project ownership and snapshot only development configuration, PostgreSQL roles/database, uploads, and Redis state. Keep secrets and backups on the server with restricted permissions.
  2. Create the isolated database and roles. Restore the rehearsal dump in one transaction with --no-owner --no-acl --role=uar_schema_owner --single-transaction --exit-on-error. For a trusted extension in the dump, grant the owner temporary database CREATE permission for restoration and revoke it afterward.
  3. Verify table inventory, migration ledgers, and object ownership. Run both checked-in migration histories and the runtime grant checks. Preserve encryption keys, OIDC signing keys and cookie keys from development.
  4. Restore uploads and Redis consistently. Verify image digests, database TLS, directory CA/hostname, integration egress, assets, OIDC and login before routing users to the replacement.
  5. At final cutover, suspend reconciliation, stop development writers and schedulers, take a final coordinated backup, repeat the tested restore, and verify migration/grant checks. Change only development proxy upstreams once the replacement is healthy.
  6. After successful cutover, stop remaining development Docker services. Retain Docker volumes and backups for recovery. Once Kubernetes accepts writes, rollback must account for those new writes; simply restarting the old database loses them.
  7. Resume reconciliation and verify a second release. Restore previously enabled scheduler behavior only after confirming that each processor has one active owner.

Infrastructure owns PostgreSQL/Redis volumes. Application manifests own upload/ClamAV volumes so WaitForFirstConsumer binding can complete with their consumers. CPU quota includes simultaneous portal/auth surge replicas.

Manual setup order

1. Install pinned K3s; disable bundled Traefik and ServiceLB.
2. Restrict API/kubelet listeners to node and pod traffic; preserve existing ingress.
3. Install Flux source-controller and kustomize-controller.
4. Apply reviewed bootstrap namespace, RBAC, storage, quotas and policies.
5. Configure secrets, HTTPS origins, registry access and integration allowances.
6. Push dev; wait for successful GitHub checks and deploy/dev publication.
7. Apply bootstrap/flux-source.yaml and verify matching-release readiness.
8. Validate login, OIDC, assets, migrations and recovery before enabling workflows.

Public import preserves maintained source, tests and immutable migrations. Private historical audit/release reports, local agent configuration and environment-specific clone experiments were omitted; the old duplicated my-app/my-app tree is removed from this branch.
