# Batch Account Reconciliation

Use this runbook when a batch is `reconciliation_required`, when cancellation reports an unresolved directory outcome, or when a legacy CSV batch has no durable `BatchAccountItem` rows.

Every newly created AD batch item has captured directory DN/object GUID evidence, is confirmed disabled after password and expiration setup, and uses the batch item itself as its lifecycle owner. The batch ID identifies the shared operation and tracking reference; no synthetic access request is created. Operators explicitly enable a completed batch item through Account Lifecycle when it should become usable. Historical items with an existing `accessRequestId` remain request-governed. Historical no-request AD items remain unresolved until their live state and immutable identity are reconciled. VPN items link the live VPN record back to the exact batch item when the relationship is unambiguous.

The reviewed creation form also sends a stable submission key. A repeated submission returns the already tracked batch and starts no duplicate work; per-account advisory locks and the processing lease remain the controls for username/email contention and worker ownership.

1. Stop retry and cancellation attempts for the batch. Record its ID and open an incident or change ticket.
2. For every requested AD username, perform a read-only directory lookup. Record whether it is absent, its enabled state, DN, and object GUID. For new tracked items, require the live DN and object GUID to match the stored batch-item evidence before mutation.
3. Treat lookup errors, missing or malformed `userAccountControl`, enabled accounts, missing immutable evidence on newly tracked rows, and identity mismatches as unresolved. Escalate them for identity review; do not delete, disable, or expire them automatically. Never treat an LDAP extension attribute or description as portal ownership.
4. During creation compensation, use the authenticated per-batch cancellation endpoint and record its typed outcome (`deleted`, `already_absent`, or an unresolved reason). After a batch has completed, do not use cancellation or offboarding: confirm disabled/revoked state and use Account Lifecycle, which records an independent action for every AD or VPN record.
5. Pre-migration item rows with all tracking fields null retain the old, narrowly constrained cancellation check: exact batch creation correlation in `description`, disabled state, and recent creation. This is legacy creation-compensation evidence, not ownership, and it is never used for newly tracked rows. Legacy CSV batches with no per-account ledger still require manual reconciliation against the source CSV and directory; do not infer a request link from username/email or mark the batch cancelled from the summary alone.
6. Retry a batch only after every target is absent or otherwise resolved and the batch no longer has `reconciliation_required` items.

For permanent retirement, Account Lifecycle deletes only the live AD object and/or live VPN Management row and its encrypted credential. It retains the batch item, lifecycle action/history, status/activity logs, comments, request linkage, and audit records. For AD, confirm the current disabled object and review a new deletion plan whenever the recorded plan or action says it used an earlier deletion method. The processor performs its final supported AD read and immutable-GUID delete on one bound connection, but another AD administrator can change the object in the small interval between them; record that race as reconciliation evidence rather than replaying the old confirmation.

If cancellation crashes after claiming the batch, the endpoint attempts to move it to `reconciliation_required`. If the database was unavailable and it remains `rolling_back`, restore database availability, capture the row and audit history, and obtain two-person approval before changing the status to `reconciliation_required`; then rerun this procedure.

## Submission-key migration

Apply `20260831010000_batch_submission_idempotency` before deploying application code that requires the key. The migration is additive: historical batches keep a null key and new reviewed submissions receive a unique key. If the application must be rolled back, leave the nullable column and unique index in place; the prior application ignores them. Do not drop the index while any instance can accept keyed submissions. A forward recovery should restore the keyed application and verify that replaying one known non-production submission returns the same batch ID without adding an audit row or starting LDAP/VPN work.

Apply `20260904170000_batch_account_lifecycle_ownership` before code that creates standalone batch owners. It is additive and preserves historical request links. Its VPN backfill links only one exact completed item to one exact case-insensitive VPN row in the same batch; row or item ambiguities stay null for reconciliation. It does not invent an AD enabled/disabled state during migration. Application rollback may leave the nullable relation and additive lifecycle columns in place. Forward recovery must restore the matching application, confirm new AD items have `lifecycleOwnerKind = batch_item` with no request link and a confirmed `disabled` projection, and verify a disabled non-production item is discoverable in Account Lifecycle before any destructive test.
## Infrastructure sync directory descriptions

Infrastructure sync no longer creates or executes LDAP metadata tasks. Existing `InfrastructureTaggingTask` rows are retained as legacy evidence, but their retry endpoint is retired; do not reset or replay them. Reconcile portal username ownership without writing request metadata to LDAP. A legacy task left in `processing` has an unknown historical external outcome and must be checked read-only in LDAP before its incident is closed.
